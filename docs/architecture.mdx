# Architecture

Bombay Entity gives a stable logical entity identity to a temporary Actorpass
incarnation. It owns activation coordination, admission, stable routing,
draining, passivation, and lifecycle facts. Actorpass owns execution of exact
incarnations. Applications own behavior construction and any persistence used
while preparing a behavior.

```text
CQRS application
    | commands addressed by EntityId
    v
Bombay Entity
    | activation, admission, routing, draining, passivation
    v
Actorpass
    | exact actor incarnation execution
    v
Behaviorpass + Communication + Observe
```

Repositories, journals, snapshots, aggregate business logic, event
serialization, projections, business idempotency, distributed discovery, and
consensus are outside this crate.

## Identity and ownership

`EntityId<I>` names a logical entity. `ActivationId` identifies one activation
attempt and resulting incarnation. An actor address or reference identifies
only that exact incarnation and is never the stable entity identity.

Activation IDs are allocated monotonically from a directory-wide namespace and
must never wrap. Exhaustion is an explicit runtime failure. Inactive entities
are normally absent from the directory, preventing memory use from growing with
every entity ever addressed.

Each directory value is an `Arc<Slot>`. Slot pointer identity is the sole
authority for removing a map binding: removal succeeds only while the current
map value is the same slot allocation captured by the lifecycle effect. One
slot allocation is never reused for another activation, so a delayed removal
cannot delete a replacement binding.

Activation identity has a separate authority inside that slot's lifecycle
machine. It prevents delayed activation, completion, passivation, or
termination facts from changing the state of a different incarnation. It is
not a second map-removal condition.

## Application and incarnation ports

Applications use the high-level facade; they do not submit lifecycle facts or
manually interpret effects:

```rust
entities.dispatch(EntityId::new(42), command).await?;
```

An actor runtime implements `LocalEntityRuntime` once. That port supplies task
ownership, transactional activation, exact-incarnation delivery, the ordered
fence, and affine retirement. The facade feeds every asynchronous result back
through the directory's authoritative lifecycle driver. `DirectoryOutput` and
`EffectInterpreter` are integration-level APIs rather than application
workflow.

The application prepares a behavior without exposing persistence concepts to
the entity runtime:

```rust
trait EntityDefinition {
    type Id;
    type Command;
    type Behavior;
    type Error;

    fn prepare(
        &self,
        id: &EntityId<Self::Id>,
    ) -> impl Future<Output = Result<Self::Behavior, Self::Error>> + Send;
}
```

Preparation may load state from a repository, construct a new aggregate, use a
cache, or perform no I/O. Bombay Entity does not distinguish these cases.

The incarnation runtime transactionally initializes and launches the behavior:

```rust
trait IncarnationRuntime<D: EntityDefinition> {
    type Endpoint: EntityEndpoint<D::Command>;
    type Lease: IncarnationLease;
    type Error;

    fn activate(
        &self,
        behavior: D::Behavior,
    ) -> impl Future<
        Output = Result<Activated<Self::Endpoint, Self::Lease>, Self::Error>,
    > + Send;
}
```

`activate` returns only after behavior initialization and initialization effects
succeed, exact-incarnation registration commits, and the initialized event loop
is launched. Actorpass should expose a focused operation backed by its existing
provisional typestate; the typestate itself need not become public.

An activated incarnation returns separate capabilities:

```rust
struct Activated<E, L> {
    endpoint: E,
    lease: L,
}

trait EntityEndpoint<C> {
    type Error;

    fn deliver(
        &self,
        command: C,
    ) -> impl Future<Output = Result<(), DeliveryFailure<C, Self::Error>>> + Send;
}

trait IncarnationLease {
    type Outcome;

    fn request_graceful_retirement(&self);
    fn force_abort(&self);
    fn terminated(self) -> impl Future<Output = Self::Outcome> + Send;
}
```

The endpoint may be cloned but grants no retirement authority. The affine lease
owns graceful retirement, forced cancellation, and exact terminal observation.
The concrete signatures may evolve while this capability separation remains.

Before entity-directory commitment, the endpoint remains private and is not
reachable through the stable entity API. Raw Actorpass addresses and references
must not be exposed by that API. If an activation becomes stale before entity
commitment, the runtime retires the exact returned lease and awaits termination
before completing cleanup.

## Activation ownership

Activation belongs to the directory, not to the dispatch that discovers the
inactive entity:

```text
first dispatch claims Activating(g)
    -> directory starts an owned activation task
    -> first and later dispatches become bounded waiters
    -> preparation constructs the behavior
    -> incarnation runtime transactionally activates it
    -> directory validates slot identity and g
    -> directory commits Active(g, endpoint, lease)
```

Dropping a dispatch future while its command is still a bounded activation
waiter drops that command and releases only its waiter seat. It does not cancel
shared activation. Once active-delivery ownership has linearized and moved the
command into a spawned delivery task, dropping the waiting future does not
retract that delivery. A waiter is never transferred silently to a later
activation ID and the runtime never retries its command automatically.

The directory-owned task must clean up preparation failure, incarnation
activation failure, and stale validation by submitting the corresponding typed
fact. Panic and task cancellation cannot be cleaned up by the task itself;
the runtime port's `spawn` contract therefore requires driving every spawned
task to completion, and a runtime that cannot guarantee this must treat task
loss as a supervisor-level concern. No graceful terminal path may strand an
`Activating` slot or leak an incarnation lease.

## Slot state machine

The reference slot is a functional core. It consumes an owned state and one
typed fact, then returns an owned next state and an ordered effect batch:

```text
EntitySlot<C, E, L> × SlotEvent<C, E, L>
    → SlotDecision<C, E, L>
    = EntitySlot<C, E, L> × SlotEffectBatch<C, E, L>
```

State-specific reducers handle `Inactive`, `Activating`, `Active`, `Draining`,
and `Retiring`; the top-level reducer only dispatches over that product of sum
types. Policy choices and asynchronous results enter as typed facts. The core
does not acquire locks, start tasks, read clocks, or invoke endpoints.

## Machine execution

`bombay-transition` remains the allocation-free `no_std` description and
composition layer. It does not gain locks, queues, or runtime policy.

`bombay-machine-executor` provides two deliberately distinct execution laws.
`SerializedExecutor<M>` queues inputs and completes each synchronous output
handler before advancing the next transition. This is the run-to-completion law
required by behavior and actor lifecycle turns. Each submission has a receipt;
transition or handler panic poisons the executor and resolves queued receipts as
poisoned rather than silently stranding them.

`LinearizedExecutor<M>` advances inputs immediately and enqueues outputs at the
same linearization point. One caller dispatches those outputs in order while
concurrent and reentrant calls contribute work. Its non-owner return is
explicitly fire-and-forget. Entity uses this policy because lifecycle admission
must close at transition linearization while asynchronous operations return
later as typed facts. A handler panic drops its current output exactly once and
a later dispatcher resumes the remaining queue.

The executor knows nothing about entities, activation, delivery, draining,
Actorpass, or asynchronous executors. The entity directory supplies stable
keyed ownership and interprets each `LifecycleOutput` as entity runtime
capabilities. This prevents synchronization and reentrancy mechanics from
being duplicated inside entity lifecycle policy while keeping the pure machine
independently executable and structurally interpretable.

`SlotEffectBatch` is an ordered monoid: the empty batch is its identity and
concatenation preserves effect order. The effectful directory interpreter folds
that algebra into Actorpass operations, tasks, replies, telemetry, and map
updates. Rust ownership keeps commands and the affine incarnation lease unique
through every reduction without requiring `Clone`.

Reservation cardinality is also represented as a sum type—`Drained` or
`Pending(NonZeroUsize)`—rather than using zero as a hidden control convention.
This makes the fence transition available only from an explicitly drained
reservation state.

The external lifecycle is deliberately small:

```text
Inactive
  -> Activating(activation_id)
  -> Active(activation_id, incarnation)
  -> Draining(activation_id)
  -> Retiring(activation_id)
  -> Inactive
```

Internally, inactive normally means absence from the map. The implemented
slot state is:

```text
Activating {
    activation_id,
    bounded_waiters,
}

Active {
    activation_id,
    endpoint,
    lease,
    reservations,
}

Draining {
    activation_id,
    endpoint,
    lease,
    drain_progress,
}
```


Every asynchronous result carries `EntityId` and `ActivationId`. All slot
transitions validate both slot allocation and activation ID.

## Linearization points

Each entity slot is a linearizable concurrent object. Different slots progress
independently.

1. **Activation claim:** absence becomes `Activating(g)`.
2. **Activation commit:** validated `Activating(g)` becomes
   `Active(g, endpoint, lease)`.
3. **Dispatch reservation:** `reserved_dispatches` increments while the slot is
   still `Active(g)`.
4. **Passivation start:** `Active(g)` becomes `Draining(g)`, atomically closing
   admission.
5. **Dispatch resolution:** a reserved delivery either completes enqueue or
   returns its command, then releases its reservation.
6. **Fence start:** draining observes zero reservations and begins the ordered
   fence enqueue.
7. **Retirement:** successful fence acknowledgement permits graceful retirement.
8. **Removal:** exact incarnation termination permits compare-slot-and-activation
   removal.

No directory lock or slot lock is held while awaiting, invoking application or
actor code, publishing telemetry, consulting a clock, or running policy code.

## Admission and command ownership

Activation waiters and active dispatch reservations have independent bounds.
Global activation and waiter limits may be added without changing per-slot
semantics.

A dispatch against `Active(g)` proceeds as follows:

1. reserve one dispatch while holding the slot lock;
2. release the lock;
3. deliver the command;
4. on success, release the reservation after enqueue completes;
5. on failure, release the reservation and return the original command.

Passivation may start after reservation and before enqueue. The reservation
makes the drainer wait until that operation either enqueues or fails. Delivery
errors recover non-`Clone` commands. Activation and draining refusals do the
same.

The runtime does not retry commands. Reply timeout or caller cancellation does
not prove that a command was unprocessed. Business idempotency and recovery
remain application responsibilities.

## Entity processing fence

Bombay Entity initially owns the pure behavior wrapper:

```text
bombay_entity::EntityBehavior<B>
    implements Behavior
    wraps B
    receives EntityProtocol<B::Msg>

EntityProtocol<C>
    = Command(C)
    | DrainFence(FenceReply)
```

Domain commands are forwarded unchanged. A drain fence leaves inner behavior
state unchanged and emits only its acknowledgement effect, or guarantees that
the acknowledgement is the final relevant effect. The design does not infer
cross-lane ordering between independent effect lanes.

Graceful draining is:

```text
close admission
    -> wait for reserved_dispatches == 0
    -> enqueue fence on the same ordered user lane
    -> await fence acknowledgement
    -> request priority graceful retirement
    -> await exact incarnation termination
    -> remove matching slot and activation
```

The proof requires an explicit Bombay Communication premise: every completed
earlier user-lane enqueue is observed before a subsequently enqueued fence.
Focused tests must attempt to invert that order under concurrent producers and
bounded backpressure.

Actorpass interprets a transition's effects before receiving the next event.
Consequently, a received fence acknowledgement certifies completion of earlier
command transitions and their interpreted effects. Enqueue success alone does
not certify processing, and missing acknowledgement proves neither completion
nor non-completion.

Fence failures are explicit:

The implemented failure classification is:

```rust
enum FenceFailure {
    Enqueue,
    Acknowledgement,
}
```

This wrapper stays in Bombay Entity until another non-entity consumer
demonstrates that it is a general Behaviorpass capability.

## Graceful and forced draining

Drain policy is explicit:

```rust
enum DrainPolicy {
    Graceful,
    Bounded { timeout: Duration },
}

enum DrainStage {
    Reservations,
    FenceEnqueue,
    FenceAcknowledgement,
    Retirement,
}
```

Graceful policy waits for the proof sequence without a deadline. Bounded policy
may force-abort after its deadline and must report the stage at which progress
stopped.

Forced cancellation before fence acknowledgement has unknown command
completion: commands may have produced none, some, or all effects. A timeout
while awaiting termination after successful fence acknowledgement is different:
command processing is known complete even though actor retirement is stuck.
Telemetry and outcomes distinguish these cases and never label forced
retirement as graceful passivation.

## Observation and telemetry

Exact-incarnation termination and stable entity availability are separate
facts. Observing an incarnation reports the terminal outcome of one activation
ID. Observing an entity reports directory lifecycle without promising that a
particular incarnation remains live.

Telemetry publication is design intent and is not yet implemented. When
added, it publishes activation, admission rejection, draining, fence,
passivation, forced retirement, failure, and stale-event facts. Telemetry grants
no entity-control capability and is emitted after state transitions, outside
locks.

## Correctness invariants

1. At most one activation attempt is owned for an entity ID.
2. At most one activation is committed and entity-routable for an entity ID.
3. No endpoint is committed before initialization and initialization effects
   succeed.
4. No dispatch reservation begins after draining linearizes.
5. Fence enqueue begins only after every pre-existing reservation resolves.
6. Graceful retirement begins only after fence acknowledgement.
7. Forced retirement is separately classified and makes no false completion
   claim.
8. Only matching activation identity may change exact-incarnation lifecycle
   state, and only matching slot pointer identity may remove a map entry.
9. Caller cancellation cannot cancel shared activation or strand slot state.
10. Lifecycle effect interpretation and actor-runtime, telemetry, clock, and
    policy callbacks never run under directory locks. User-defined `Hash` and
    `Eq` for the entity identifier do execute inside shard `HashMap` operations
    and must not reenter the same directory.

## Verification strategy

The state machine, machine executor, directory, and runtime facade remain
independent of Actorpass. Deterministic tests cover lifecycle decisions,
command ownership, cancellation, reentrant interpretation, exact retirement,
and the concise asynchronous API. The bounded trace test enumerates the finite
event alphabet and compares every successor with the independent structural
model while checking declared-edge evidence.

Five abstract Loom protocol models explore activation claim, delivery/drain
ordering, slot-replacement removal, admission racing, and
cancellation/activation ownership interleavings, and three further Loom models
drive the real machine executors.
Retained stress tests exercise one hot identifier and many independent
identifiers across shards. A byte-oriented fuzz target is not retained because
there is no parser, unsafe code, or unconstrained input structure, and the pure
finite transition alphabet is enumerated directly; Loom covers the concurrent
nondeterminism that ordinary fuzzing would sample weakly.

Miri is not available in the pinned Rust 1.96 Nix toolchain (`cargo miri`
reports that no such command is installed). The implementation contains no
`unsafe` blocks. The reproducible gates are workspace tests, strict all-target
Clippy, the retained Loom and stress tests, both benchmarks, LLVM coverage, and
all ten flake checks.

## Research basis

### Concurrent directory workload and baseline

The local directory is optimized for many logical identifiers with mostly
independent traffic, while remaining correct when many callers contend on one
hot identifier. The adversarial workload includes concurrent first dispatch,
waiter cancellation during activation, delivery racing with passivation, stale
activation and termination completions, and bounded drain failure. Lookup is
expected to be short relative to activation, mailbox enqueue, and retirement.

The first implementation uses a fixed power-of-two array of
`Mutex<HashMap<EntityId<I>, Arc<Slot>>>` shards and a separate `Mutex` in each
slot. A hash selects exactly one shard. The shard lock only finds, inserts, or
conditionally removes an `Arc`; the slot lock only submits one fact to the pure
lifecycle machine and installs its successor. Neither lock is held while an
effect is interpreted. Poisoning is treated as an invariant violation rather
than silently exposing partially updated state.

This is a measured baseline, not an assertion that locks always outperform
specialized maps. Shalev and Shavit's split-ordered lists provide lock-free
expected-constant-time growth, and Maier, Sanders, and Dementiev demonstrate
the importance of layout and workload when comparing concurrent hash tables.
Those algorithms require substantially more resizing and reclamation machinery.
Rust's standard `HashMap` already supplies a cache-conscious SwissTable lookup
layout, while `Arc` safely delays slot reclamation until every operation drops
its reference. Epoch or hazard-pointer reclamation therefore adds no required
correctness property at this stage. A different table is justified only by
retained directory benchmarks showing shard lookup or resize contention is
material under the stated workloads.

Rust 1.96 provides `Arc`, `Mutex`, `HashMap`, and lock-free `AtomicU64` on the
supported 64-bit targets. Activation and dispatch sequences use relaxed atomic
increments because uniqueness depends only on each atomic modification order;
slot mutexes establish the state-transition happens-before relationships.
Sequence wrap is rejected rather than reused, preventing an ABA-like identity.
Effect batches store zero or one effect inline, so the steady active-delivery
path does not allocate for lifecycle effects. Multi-effect activation completion
allocates only when ownership of several bounded waiters must be released.

The directory linearization points refine the lifecycle points above:

1. **Stable slot claim:** insertion of a newly allocated slot while holding its
   shard lock. A losing caller discards its candidate and uses the installed
   allocation.
2. **Lifecycle fact:** replacement of the machine successor while holding the
   slot lock. The emitted `TransitionEvidence` is retained with that decision.
3. **Admission close:** installation of the `Draining` successor for
   `BeginDrain`; later dispatch facts observe closed admission.
4. **Effect order:** one interpreter ownership token per slot serializes an
   ordered effect queue. Follow-up facts append effects through the same path,
   so reentrancy cannot start a second interpreter.
5. **Removal:** while holding the shard lock, removal occurs only if
   `Arc::ptr_eq` matches the captured slot. Pointer identity is the exact
   removal authority because one slot allocation never serves a second
   activation. A caller that already cloned the old `Arc`
   remains memory-safe but cannot mutate a replacement entry.

### Baseline measurements

`crates/entity/benches/directory.rs` is a dependency-free retained benchmark
that measures a hot activating slot, a hot active incarnation with synchronous
delivery resolution, insertion of independent identifiers, and eight-thread
contention on one active incarnation. On 2026-08-11, an Apple
M4 Pro running Darwin 25.5.0 and the Rust 1.96 release profile produced the
following final-tree minimum and median over seven repetitions:

```text
iterations=1000000
repetitions=7
activating_hot_key_min=70.678875ms
activating_hot_key_median=70.821875ms
active_hot_key_min=138.632875ms
active_hot_key_median=138.795667ms
independent_iterations=100000
independent_keys_min=15.002458ms
independent_keys_median=15.494375ms
threads=8
contended_iterations_per_thread=100000
contended_active_key_min=243.755875ms
contended_active_key_median=244.999166ms
stale_absent_callbacks_min=38.083542ms
stale_absent_callbacks_median=38.105125ms
```

The minimums correspond to about 70.7 ns per activating-slot submission, 138.6
ns per active delivery and resolution, 150.0 ns per new independent slot, and
304.7 ns per contended active delivery and resolution. Every lifecycle output
is interpreted, so the benchmark does not accumulate a synthetic pending-effect
backlog. These dated final-tree measurements are regression references, not
cross-machine comparisons; the controlled baseline comparison is retained in
`.tighten/BASELINE.md`.
